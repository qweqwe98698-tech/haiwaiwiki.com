faq:
  - q: 为什么 Telegram 只有全局模式才能连接?
    a: 它不走常规的 HTTP/HTTPS 域名请求,而是用 MTProto 协议直连 IP 段。按域名匹配的分流规则匹配不到,流量就走了直连。全局模式强制所有流量走代理,所以能用。正确解法是补上 IP 段规则或用 TUN 模式。
  - q: 收不到登录验证码怎么办?
    a: 先确认验证码的下发方式——Telegram 优先发到你已登录的其他设备,而不是短信。完全没有其他设备时才走短信,此时收不到多与运营商和号码归属有关,与代理关系不大。切换节点地区不会改变验证码的下发渠道。
  - q: Telegram 能连上但消息发送很慢?
    a: 多为节点延迟或丢包导致,与解锁无关。换同地区其他节点测试;只在晚高峰慢则是线路拥堵问题,见延迟分层排查。
  - q: 文件下载速度很慢是什么原因?
    a: Telegram 的文件传输对带宽和并发都敏感,低价套餐的限速、节点负载、以及倍率节点都会影响。先换节点对比,再看套餐是否有速率限制。
  - q: 用 Telegram 需要原生 IP 吗?
    a: 一般不需要。Telegram 对 IP 类型的敏感度远低于流媒体和 AI 服务,普通节点通常够用。频繁触发风控验证的情况多与账号行为有关,而不是节点类型。
  - q: 桌面端能用手机不能用怎么办?
    a: 两端的代理配置是独立的。手机上确认 VPN 已连接、且 Telegram 未被系统的省电或网络限制策略挡住;必要时在手机客户端里切到全局模式验证一次,确认是不是规则问题。

Telegram 的连接问题有个很典型的特征:**其他网站都正常,只有它连不上;
或者切到全局模式就好了**。原因在于它的通信方式和普通网站不一样。

## 为什么分流规则容易漏掉它

多数分流规则是按**域名**匹配的——你访问 `example.com`,规则命中,流量走代理。
但 Telegram 用的是 MTProto 协议,客户端直接连接它的服务器 IP 段,
过程中不产生可供规则匹配的域名请求。结果就是:规则匹配不到 → 流量走直连 → 连不上。

全局模式之所以有效,是因为它不做匹配,所有流量一律走代理。
但**长期开全局并不合适**:国内网站也会绕道海外,变慢且浪费流量。

### 三种正确解法

1. **补规则**:在客户端里为 Telegram 的 IP 段添加代理规则。
   多数机场的订阅配置已经内置了这类规则——**先更新一次订阅**,通常就能解决;
2. **用 TUN 模式**:TUN 接管全部流量(包括不读系统代理的应用),
   适合桌面端。注意 TUN 本身可能出问题,见
   [能测速但打不开网页](/tutorial/connected-but-no-internet/)的 TUN 部分;
3. **应用内代理**:Telegram 客户端自带代理设置,可以单独填入 SOCKS5 或 MTProto 代理。
   这条路绕开了系统分流,但需要机场提供对应信息。

## 验证码收不到

这是另一类问题,和代理关系不大。Telegram 的验证码下发有优先级:

- **优先发到你已登录的其他设备**(Telegram 应用内消息);
- **只有在没有任何已登录设备时**,才会考虑短信。

所以「收不到短信」的常见真相是:验证码已经发到你的另一台设备上了。
真的走短信却收不到时,原因通常在运营商侧与号码归属地,
**换节点地区不会改变下发渠道**。

## 连上了但很慢

连接成功之后的速度问题,和 Telegram 本身无关:

| 现象 | 方向 |
| --- | --- |
| 消息发送延迟高 | 节点延迟或丢包,换节点;只在晚高峰慢见[延迟分层排查](/airport/high-latency/) |
| 文件下载慢 | 带宽或套餐限速;注意倍率节点会加快流量消耗 |
| 频繁掉线重连 | 链路抖动或长连接被中断,见[网络环境差异](/tutorial/network-environment-issues/) |

## 需要什么样的节点

Telegram 对 IP 类型不挑剔——它不像流媒体和 AI 服务那样依赖
[原生 IP](/protocol/native-ip/)。普通节点通常够用,你更该关注的是延迟稳定性。

如果你频繁遇到账号风控验证,那多与账号行为(新号、频繁加群、多设备登录)有关,
换更贵的节点通常解决不了这个问题。
