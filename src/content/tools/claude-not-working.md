Claude 和 Gemini 的访问问题与 [ChatGPT](/tools/chatgpt-not-working/) 同源——
都是**地区判定**加**出口 IP 风控**两层机制。但三家的支持地区列表、风控策略、
IP 黑名单各自独立,所以会出现「ChatGPT 能用、Claude 不行」这种情况。

这一页只讲与 ChatGPT 不同的地方,共通的排查流程直接沿用那一篇。

## 先确认节点的实际落地地区

这是最常见的误判来源:**节点名不等于实际出口位置。**
标着「日本」的节点,实际出口可能在别处(广播 IP 的典型表现,
原理见[原生 IP 词条](/protocol/native-ip/))。

验证方法:连上节点后,用任意 IP 查询服务看当前出口 IP 的实际归属地,
再对照目标服务的支持地区。这一步能省掉很多无效尝试。

## Claude 的注意点

- **地区列表与 ChatGPT 不完全相同**,能开 ChatGPT 的节点不保证能开 Claude;
- **对话中断**:长回复是长连接场景,出口 IP 中途变化会让服务端判定会话异常。
  如果你经常遇到生成到一半中断,问机场「出口 IP 是否固定」——
  这正是[ChatGPT 机场推荐](/airport/chatgpt/)购前清单里的第三项;
- **网页能用、客户端或 API 不行**:通常是分流规则只覆盖了网页域名,
  切全局模式验证一次即可确认。

## Gemini 的注意点

Gemini 多了一个与代理无关的变量:**Google 账号本身的地区设置**。

换了受支持地区的节点仍提示不可用时,检查账号的国家/地区配置是否与节点一致。
这一项在账号设置里,改了之后可能需要等待生效——排查时别把它算在机场头上。

## 通用排查顺序

与 ChatGPT 完全一致,按命中率排序:

1. 换一个标注 AI 可用的节点(IP 质量是首要原因);
2. 确认节点**实际**落地地区在支持列表内;
3. 清除该站点 Cookie 后重试,让服务端重新判定;
4. 检查分流规则是否覆盖了该服务的全部域名(切全局模式验证);
5. 用无痕窗口排除浏览器插件干扰;
6. 以上都试过,带着结果问机场客服哪些节点当前可用。

每一步的原理说明见 [ChatGPT 无法访问怎么办](/tools/chatgpt-not-working/),
这里不重复。

## 如果你同时用多个 AI 服务

把它们**分别**列进购买前的验证清单,不要假设一个能用其他都能用。
用最短周期购买、在你的常用时段逐个实测,是唯一可靠的确认方式——
选购维度见 [ChatGPT 机场推荐](/airport/chatgpt/),那一页的判断标准对 Claude、
Gemini 同样适用。
