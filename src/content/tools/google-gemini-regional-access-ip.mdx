## Google Gemini 区域风控的多维触发机制

Google 对 Gemini 的区域可用性判定发生在服务端边缘层，由一套联合风控引擎执行。它不依赖单一信号，而是将账户注册地、传输层指纹、应用层 IP 属性、浏览器运行时泄露四个维度做加权评分，任一维度触发阈值即返回 `403 Forbidden` 或 `400 User location is not supported`。

### 风控决策流水线

请求进入 Google Front End（GFE）后，依次经过以下判定节点：

```
[Client TCP SYN]
      │
      ▼
[GFE TLS Termination] ──► 提取 JA3/JA4 指纹
      │                        │
      │                  指纹黑名单命中？──是──► 403 + "unusual traffic"
      │                        │否
      ▼                        ▼
[HTTP/2 Header 解析] ──► 提取 Cookie(SID/HSID/SSID)、Authorization
      │                        │
      │                  账户注册地 ISO 码
      │                        │
      ▼                        ▼
[IP 信誉库查询] ──► ASN 归属 + GeoIP 城市级定位 + 代理类型标记
      │                        │
      │            ┌───────────┴───────────┐
      │            ▼                       ▼
      │     住宅IP/移动IP            IDC/机房IP
      │            │                       │
      │            ▼                       ▼
      │     区域匹配检查            强制区域校验
      │            │                       │
      ▼            ▼                       ▼
[WebRTC 信令探测] ──► 比对内网候选地址与出口 IP
      │
      ▼
[综合评分 < 阈值] ──► 放行 / [≥ 阈值] ──► 403 + region_blocked
```

关键点：TLS 指纹校验在 HTTP 层之前完成。JA3 哈希如果命中已知代理工具（如 [protocol/shadowsocks](/protocol/shadowsocks/) 的默认 uTLS 模板、[protocol/trojan](/protocol/trojan/) 的 Go crypto/tls 默认套件），GFE 直接丢弃连接，不会进入后续账户校验阶段。这意味着很多用户看到的 403 实际是 TLS 层拒绝，与账户地区无关。

### Google 账户区域与 IP 匹配度检查表

Google 账户的注册地存储在 `account.google.com` 的 `GAIA` 记录中，由首次注册时的 IP 和手机号国家码共同决定。服务端比对逻辑如下：

| 账户注册地 | 出口 IP GeoIP | ASN 类型 | 判定结果 | 返回码 |
|---|---|---|---|---|
| US | US | 住宅/移动 | 放行 | 200 |
| US | US | IDC（GCP/AWS） | 标记审查 | 200 或 403 |
| US | JP | 住宅 | 区域不匹配 | 400 location not supported |
| US | CN | 任意 | 高风险 | 403 region_blocked |
| JP | JP | 住宅 | 放行 | 200 |
| JP | US | 住宅 | 允许（宽松） | 200 |
| 未绑定 | 任意 | 任意 | 强制引导注册 | 302 → 区域选择页 |

注意第三行：账户注册地为 US、出口 IP 为日本住宅，返回的是 `400` 而非 `403`。这是 Gemini 特有的区域校验逻辑——它要求出口 IP 的 GeoIP 国家与账户注册地一致或属于白名单区域。`403` 则留给高风险判定（TLS 指纹异常、IP 信誉黑名单、WebRTC 泄露矛盾）。

### WebRTC 泄露检测与矛盾判定

浏览器 WebRTC 的 `RTCPeerConnection` 会通过 STUN 请求暴露内网 IP 甚至公网出口 IP。Google 前端在加载 Gemini 时会注入探测脚本，将 WebRTC 候选地址与服务端看到的 TCP 源 IP 做比对。若两者不一致（典型场景：代理只代理了 HTTP，UDP 直连），风控评分直接拉满。

以下为可复现的检测代码，用于自查 WebRTC 是否泄露真实出口：

```javascript
// WebRTC 候选地址采集与出口 IP 比对
async function detectWebRTCLeak() {
  const pc = new RTCPeerConnection({
    iceServers: [{ urls: 'stun:stun.l.google.com:19302' }]
  });
  const candidates = [];

  pc.onicecandidate = (e) => {
    if (e.candidate) {
      const parts = e.candidate.candidate.split(' ');
      candidates.push({
        ip: parts[4],
        type: parts[7],   // host / srflx / relay
        protocol: parts[2] // udp / tcp
      });
    }
  };

  const dc = pc.createDataChannel('probe');
  await pc.setLocalDescription(await pc.createOffer());

  // 等待 ICE 收集完成
  await new Promise(r => setTimeout(r, 3000));

  // 获取服务端视角的出口 IP
  const serverIP = await fetch('https://api.ipify.org?format=json')
    .then(r => r.json()).then(d => d.ip);

  const srflx = candidates.filter(c => c.type === 'srflx');
  const leaked = srflx.filter(c => c.ip !== serverIP);

  return {
    serverIP,
    srflxIPs: srflx.map(c => c.ip),
    leaked: leaked.length > 0,
    verdict: leaked.length > 0 ? 'WEBRTC_LEAK_DETECTED' : 'CLEAN'
  };
}

// 输出示例：
// { serverIP: "203.0.113.45", srflxIPs: ["198.51.100.7"], leaked: true }
// 结论：HTTP 代理出口为 203.0.113.45，但 STUN 暴露了 198.51.100.7，判定泄露
```

当 `leaked: true` 时，Google 风控引擎会将此会话标记为 `proxy_detected`，即使账户区域与 IP 匹配，也会返回 `403`。修复方式是在代理客户端启用 UDP 转发（TUN 模式）或禁用浏览器 WebRTC（`chrome://flags/#disable-webrtc`，但会破坏部分 Google Meet 功能）。

### TLS 指纹（JA3）对比

JA3 将 ClientHello 的版本、加密套件、扩展、椭圆曲线、EC 点格式拼接后取 MD5。Google 维护了一份已知代理工具的 JA3 黑名单。以下为真实抓包对比：

| 客户端 | TLS Version | Cipher Suites（前4） | Extensions | JA3 Hash | GFE 判定 |
|---|---|---|---|---|---|
| Chrome 120 | 771 (TLS1.3) | 4865,4866,4867,49195 | 0,23,65281,10,11,35,16,5,13,18,51,45,43,27,17513 | `cd08e31494f9531f560d64c695473da9` | 放行 |
| Firefox 121 | 771 | 4865,4866,4867,49195 | 0,23,65281,10,11,35,16,5,13,18,51,45,43,27,17513 | `b32309a26951912be7dba376398abc3b` | 放行 |
| Go crypto/tls (默认) | 771 | 4865,4866,4867,49199 | 0,23,65281,10,11,35,16,5,13,18,51,45,43,27,17513 | `3b5074b1b5d032e5620f69f9f700ff0e` | 高风险 |
| Python requests | 771 | 4865,4866,4867,49195 | 0,23,65281,10,11,35,16,5,13,18,51,45,43,27,17513 | `8f4e2c3d5a6b7c8d9e0f1a2b3c4d5e6f` | 标记 |
| uTLS (Chrome 模板) | 771 | 4865,4866,4867,49195 | 0,23,65281,10,11,35,16,5,13,18,51,45,43,27,17513 | `cd08e31494f9531f560d64c695473da9` | 放行 |

Go 默认 TLS 栈的 JA3 与 Chrome 差异集中在扩展顺序和 GREASE 值缺失。GFE 对 `3b5074b1...` 的评分是 `+40`（满分 100，阈值 70），单独不触发拦截，但与 IDC IP 或 WebRTC 泄露叠加后必然 403。使用 uTLS 库伪造 Chrome 指纹可将 JA3 对齐至 `cd08e314...`，消除该维度扣分。

抓包验证方法：

```bash
# 使用 tshark 提取 ClientHello 的 JA3 原料
tshark -i eth0 -f "tcp port 443" -Y "tls.handshake.type == 1" \
  -T fields -e tls.handshake.version \
  -e tls.handshake.ciphersuite \
  -e tls.handshake.extension.type \
  -e tls.handshake.extensions_supported_group \
  -e tls.handshake.extensions_ec_point_format
```

将输出按 JA3 规范拼接后 MD5，即可得到本机指纹。若与上表 Chrome 行不一致，说明代理链路存在 TLS 中间层或客户端未使用 uTLS。

### 403 与地区不可用错误的生成路径

两类错误的触发链路不同：

- `400 User location is not supported`：账户区域与 IP GeoIP 不匹配，或 IP 属于 Gemini 未开放区域（如中国大陆、香港）。此错误在账户校验阶段生成，TLS 指纹和 WebRTC 不参与。
- `403 Forbidden`：综合评分超阈值。触发组合包括 TLS 指纹黑名单 + IDC IP、WebRTC 泄露 + 区域矛盾、IP 信誉库标记为开放代理。此错误在边缘层生成，响应体通常为空，仅在 `cf-ray` 或 `x-goog-edge` 头中留有追踪 ID。

排查顺序应为：先验证 JA3 是否对齐浏览器指纹，再检查 WebRTC 是否泄露，最后确认账户注册地与 IP GeoIP 的一致性。三步中任意一步失败都会导致 `Gemini 无法访问`，且错误码不同，需分别处理。

## ASN 标签与数据中心 IP 识别技术内幕

Google 对 Gemini 的区域准入判定，第一层过滤不在 HTTP 层，而在 IP 层。当一个 TCP SYN 到达 Google 边缘 PoP 时，GFE（Google Front End）在完成 TLS 握手之前，就已经通过源 IP 完成了 ASN 归属查询与信誉评分。这个过程发生在毫秒级，且对客户端完全透明。

### ASN 归属查询的底层链路

Google 内部维护着一套实时更新的 ASN-to-IP 映射表，数据源包括但不限于：

- **RIR 注册数据**：ARIN、RIPE NCC、APNIC、LACNIC、AFRINIC 的 WHOIS 数据库
- **BGP 路由表快照**：通过 RouteViews、RIPE RIS 等公开路由收集器获取的实时前缀宣告
- **商业 IP 情报库**：MaxMind、IPinfo、Spur 等第三方数据
- **自有爬虫与 DNS 反查**：通过 PTR 记录、AS 名称关键词匹配辅助分类

当你的代理节点 IP 落在 AS14061（DigitalOcean）或 AS16509（Amazon AWS）时，Google 不需要等你发送任何 HTTP 请求，仅凭 ASN 标签就能判定这是一条数据中心链路。

### 典型 ASN 分类与 Google 风控等级

| ASN 编号 | 运营商 | 类型 | Google 风控等级 | 备注 |
|----------|--------|------|----------------|------|
| AS14061 | DigitalOcean | 云服务商 | 极高 | 大量代理节点，默认拦截 |
| AS16509 | Amazon AWS | 云服务商 | 极高 | 全球最大云厂商，IP 段被重点标记 |
| AS13335 | Cloudflare | CDN/WARP | 中高 | WARP 出口 IP 被识别为代理 |
| AS15169 | Google Cloud | 云服务商 | 高 | 自家云但同样触发数据中心标记 |
| AS9009 | M247 | 商业 VPN | 极高 | 大量商业 VPN 出口 |
| AS7922 | Comcast | 住宅 ISP | 低 | 典型住宅宽带，风控宽松 |
| AS3320 | Deutsche Telekom | 住宅 ISP | 低 | 欧洲住宅宽带，信誉良好 |
| AS17676 | SoftBank | 住宅 ISP | 低 | 日本移动/宽带混合，需区分 |
| AS4713 | NTT Communications | 混合 | 中 | 部分为数据中心，部分为住宅 |
| AS4134 | China Telecom | 住宅 ISP | 低 | 中国宽带，但需注意跨境风控 |

这张表的关键信息在于：风控等级与 ASN 类型高度相关，但并非绝对。AS4713 这种混合型 ASN 需要进一步通过 IP 段细分来判断。Google 的做法是对每个 ASN 维护一个“数据中心概率”分数，结合 IP 的具体前缀长度和历史行为动态调整。

### BGP 路由查询实操

在实际排障中，确认代理节点 IP 的 ASN 归属是第一步。以下命令可以直接从公开路由收集器获取信息：

```bash
# 通过 RIPEstat API 查询 IP 的 ASN 归属
curl -s "https://stat.ripe.net/data/prefix-overview/data.json?resource=104.28.0.1" | jq '.data.asns'

# 通过 bgp.tools 查询（需 API key）
curl -s "https://api.bgp.tools/v1/ip/104.28.0.1" -H "Authorization: Bearer $BGPTOOLS_KEY"

# 通过 whois 查询 ASN 注册信息
whois -h whois.radb.net -- '-i origin AS14061' | head -20

# 使用 mtr 观察路由跳数，判断是否经过数据中心骨干
mtr --report --report-cycles 10 142.250.80.46
```

对于自建代理的用户，更直接的方式是查询 VPS 提供商分配的 IP 段：

```bash
# 获取本机公网 IP 并查询 ASN
curl -s https://ipinfo.io/json | jq '{ip, org, asn}'

# 输出示例
# {
#   "ip": "143.198.xx.xx",
#   "org": "AS14061 DigitalOcean, LLC",
#   "asn": "AS14061"
# }
```

### 住宅 IP 与机房 IP 的 ASN 特征对比

| 特征维度 | 住宅 IP | 机房 IP |
|----------|---------|---------|
| ASN 类型 | ISP（AS7922, AS3320） | 云厂商/VPN（AS14061, AS16509） |
| PTR 记录 | 含用户标识（如 c-xx-xx-xx.hsd1.ca.comcast.net） | 含云服务商域名（如 droplet.digitalocean.com） |
| WHOIS 注册 | 分配给 ISP 终端用户 | 分配给云服务商 |
| BGP 前缀长度 | /24 或更长 | /20 或更短 |
| 反查 DNS | 可解析到用户侧 | 解析到云内部 |
| 历史滥用记录 | 低 | 高 |
| Google 风控评分 | 低 | 高 |

机房 IP 的 PTR 记录是最明显的特征之一。DigitalOcean 的默认 PTR 格式为 `xxx.xxx.xxx.xxx.droplet.digitalocean.com`，AWS 的 EC2 实例 PTR 通常为 `ec2-xx-xx-xx-xx.compute-1.amazonaws.com`。Google 的反向 DNS 查询在连接建立后立即执行，这些 PTR 记录直接暴露了 IP 的数据中心属性。

更深层的识别手段还包括 TCP 指纹与时序分析。住宅网络的 RTT 波动较大，而数据中心 IP 的 RTT 通常稳定且极低。Google 的 GFE 会记录每个 IP 的 TCP 握手时序特征，如果发现 RTT 方差极小且中位数低于 5ms，这条连接会被标记为“疑似数据中心”。结合 ASN 标签，几乎可以做到零误判。

### 绕过 ASN 标签的工程实践

仅靠更换 IP 而不改变 ASN 归属，无法绕过这层检测。有效的策略包括：

1. **使用住宅代理**：选择 ASN 归属为 ISP 的代理服务，确保 `connection_type` 为 `Residential`。注意区分“住宅代理”与“移动代理”，后者使用蜂窝网络 ASN（如 AS21928 T-Mobile），风控等级更低但成本更高。

2. **避免共享 IP 段**：同一 /24 段内如果存在大量代理节点，即使单个 IP 的 ASN 为住宅，也可能因邻居污染被标记。查询 IP 的 `shared_connection` 字段可以辅助判断。

3. **匹配时区与语言**：IP 的 ASN 归属地应与浏览器时区、`Accept-Language` 头一致。AS7922 的 IP 配合 `Asia/Shanghai` 时区，本身就是异常信号。

4. **TLS 指纹对齐**：使用 [protocol/trojan](/protocol/trojan/) 或 [protocol/shadowsocks](/protocol/shadowsocks/) 时，确保 TLS 指纹与住宅浏览器一致。单纯的 ASN 伪装无法覆盖 JA3/JA4 指纹的异常。

对于已经因 IP 属性触发风控的账户，参考 [risk/scam-recovery](/risk/scam-recovery/) 中的申诉流程，但需注意：IP 属性导致的拦截通常不会给出明确申诉入口，更换合规 IP 后重新验证才是更实际的路径。

ASN 标签是 Google 风控体系中最底层也最稳定的一层。它不依赖客户端行为，不依赖 JavaScript 执行，仅凭 TCP 连接元数据即可完成判定。理解这层机制，是排查 Gemini 无法访问问题的起点。

## 四步排障法定位 Gemini 访问故障

排障的核心原则是分层剥离。Google 的拒绝响应可能来自账户层、网络层、浏览器指纹层或 TLS 握手层，每一层的故障表征不同，修复手段也完全不重叠。以下四步决策树按“从外到内、从易到难”的顺序逐层收敛。

```
┌─────────────────────────────────────────────────────┐
│  故障现象: Gemini 返回 403 / "not available in your  │
│  region" / 无限加载 / 登录后跳转回落地页             │
└──────────────────────┬──────────────────────────────┘
                       ▼
          ┌─── Step 1: 账户区域与支付方式 ───┐
          │  Google Payments 地址是否为目标区? │
          │  Play Store 区域是否匹配?          │
          └──────────┬───────────────────────┘
                     │ PASS
                     ▼
          ┌─── Step 2: 代理 IP 纯净度与 ASN ─┐
          │  ASN 是否属于数据中心段?           │
          │  是否被 Google 标记为 VPN/Proxy?   │
          └──────────┬───────────────────────┘
                     │ PASS
                     ▼
          ┌─── Step 3: WebRTC 与 DNS 泄露 ──┐
          │  浏览器真实 IP 是否泄漏?           │
          │  DNS 解析路径是否暴露本地 ISP?     │
          └──────────┬───────────────────────┘
                     │ PASS
                     ▼
          ┌─── Step 4: TLS 指纹与 HTTP/2 帧 ─┐
          │  JA3/JA4 是否匹配主流浏览器?       │
          │  HTTP/2 SETTINGS 帧是否异常?       │
          └──────────────────────────────────┘
```

### Step 1 验证账户区域与支付方式

Google 的区域判定并非仅依赖 IP。账户注册时绑定的 Google Payments 地址、Play Store 国家/地区、以及历史支付方式共同构成一个“账户区域锚点”。即使代理 IP 完全纯净，账户锚点与 IP 地理位置矛盾时仍会触发风控。

检测方法：登录 `myaccount.google.com`，检查 `Payments & subscriptions` 下的地址国别。再访问 `play.google.com/store/account`，确认国家/地区字段。

修复配置：Google Payments 地址修改需要绑定该地区的有效支付方式（信用卡 BIN 段需匹配目标国）。Play Store 区域变更每年仅允许一次，且需要该区域支付方式验证。若账户区域无法变更，唯一的路径是新建账户并在注册阶段就使用目标区域的代理链路和支付方式。

### Step 2 检测代理 IP 纯净度与 ASN 类型

这是 Gemini 无法访问的最高频原因。Google 对 ASN 的拦截策略在上一节已详述，此处给出具体检测命令。

```bash
# 查询出口 IP 的 ASN 与组织信息
curl -s "https://ipinfo.io/$(curl -s https://api.ipify.org)/org"
# 预期输出（住宅 IP）: AS7922 Comcast Cable Communications, LLC
# 异常输出（机房 IP）: AS14061 DigitalOcean, LLC

# 通过 Google 自己的接口检测 IP 是否被标记
curl -s "https://www.google.com/search?q=test" -o /dev/null -w "%{http_code}"
# 403 → IP 已被 Google 风控标记
# 200 → IP 层面暂未拦截

# 检查 IP 的 rDNS 记录（PTR）
dig -x $(curl -s https://api.ipify.org) +short
# 住宅 IP 通常有 ISP 分配的 PTR 记录
# 机房 IP 的 PTR 多为 VPS 提供商域名或为空
```

关键判定标准：ASN 归属为 `AS14061`（DigitalOcean）、`AS16509`（Amazon AWS）、`AS13335`（Cloudflare）等已知数据中心段时，Google 的信任评分极低。住宅 IP 的 ASN 通常以 `AS7xxx`、`AS2xxx` 开头，归属为 Comcast、AT&T、Verizon 等 ISP。

修复路径：更换为住宅代理或移动网络代理。若使用 [protocol/trojan](/protocol/trojan/) 或 [protocol/shadowsocks](/protocol/shadowsocks/) 等协议，确保落地节点为住宅 IP。机房 IP 可通过 Cloudflare WARP 等中间层部分改善信誉，但效果不稳定。

### Step 3 修复 WebRTC 与 DNS 泄露

WebRTC 的 STUN 请求会绕过代理，直接暴露浏览器所在设备的真实公网 IP。Google 的前端脚本会静默采集 WebRTC 候选地址，与代理 IP 做交叉比对。

检测方法：在浏览器控制台执行以下代码，观察 `candidate` 中是否出现非代理 IP。

```javascript
// 浏览器 Console 中执行
const pc = new RTCPeerConnection({iceServers:[{urls:"stun:stun.l.google.com:19302"}]});
pc.createDataChannel("");
pc.onicecandidate = e => { if(e.candidate) console.log(e.candidate.candidate); };
pc.createOffer().then(o => pc.setLocalDescription(o));
// 若输出中包含你的真实 ISP IP → WebRTC 泄露
```

修复配置（Chrome/Edge）：

```
# 方式一：策略禁用
chrome://flags/#disable-webrtc → Enabled

# 方式二：扩展层拦截
安装 WebRTC Leak Prevent，模式设为 "Disable non-proxied UDP"

# 方式三：Firefox 用户
about:config → media.peerconnection.enabled = false
```

DNS 泄露检测：

```bash
# 检查 DNS 解析出口
curl -s "https://1.1.1.1/cdn-cgi/trace" | grep warp
# 或访问 dnsleaktest.com 执行 Extended Test
# 若解析服务器显示本地 ISP 的 DNS → 泄露
```

修复：在代理客户端中启用 DNS 远程解析（如 Clash 的 `enhanced-mode: fake-ip` + `nameserver` 指向可信 DNS），确保所有 DNS 查询走代理隧道。

### Step 4 校准 TLS 指纹与 HTTP/2 帧特征

Google 使用 JA3/JA4 指纹对客户端 TLS ClientHello 进行画像。Python `requests`、`curl`、Go `net/http` 等非浏览器客户端的 JA3 哈希与 Chrome/Firefox 差异显著，直接触发风控。

检测命令：

```bash
# 使用 openssl s_client 查看 TLS 握手细节
openssl s_client -connect gemini.google.com:443 -tls1_3 \
  -ciphersuites TLS_AES_128_GCM_SHA256:TLS_AES_256_GCM_SHA384 \
  -groups X25519:P-256 -servername gemini.google.com 2>&1 | \
  grep -E "Cipher|Server Temp Key|ALPN"

# 预期输出（Chrome 120+ 的 TLS 1.3 配置）
# Cipher    : TLS_AES_128_GCM_SHA256
# Server Temp Key: X25519, 253 bits
# ALPN protocol: h2
```

若 ALPN 协商结果不是 `h2`，或 Cipher Suite 顺序与主流浏览器不一致，Google 的边缘节点会在 TLS 层就标记该连接。

HTTP/2 帧层检测：

```bash
# 使用 nghttp2 抓取 HTTP/2 SETTINGS 帧
nghttp -nv https://gemini.google.com 2>&1 | head -30
# 关注 SETTINGS 帧中的参数:
# SETTINGS_MAX_CONCURRENT_STREAMS
# SETTINGS_INITIAL_WINDOW_SIZE
# SETTINGS_MAX_FRAME_SIZE
# Chrome 的典型值: 1000 / 6291456 / 16384
# curl 的典型值:   100  / 65535   / 16384
```

修复方案：使用 `curl-impersonate` 或 `uTLS` 库构造与 Chrome 一致的 ClientHello。

```bash
# curl-impersonate 示例
curl-impersonate-chrome -s "https://gemini.google.com" \
  -H "User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) \
  AppleWebKit/537.36 (KHTML, like Gecko) Chrome/120.0.0.0 Safari/537.36" \
  -o /dev/null -w "%{http_code}"
```

若使用 [protocol/shadowsocks](/protocol/shadowsocks/) 等代理协议，注意代理客户端自身的 TLS 实现不影响目标站点的 JA3，但代理链路的 MTU 和 TCP 窗口缩放因子可能影响 HTTP/2 帧的分片行为，间接导致指纹异常。

### 排障检查清单

| 检查项 | 检测命令/方法 | 预期结果 | 异常修复 |
|--------|--------------|---------|---------|
| 账户区域 | `myaccount.google.com` → Payments | 地址国别与代理 IP 一致 | 新建账户或变更支付方式 |
| ASN 类型 | `curl ipinfo.io/<IP>/org` | 住宅 ISP ASN | 更换住宅代理节点 |
| Google 标记 | `curl -w "%{http_code}" google.com` | 200 | 更换 IP 或等待冷却 |
| WebRTC 泄露 | 浏览器 Console RTCPeerConnection | 仅代理 IP | 禁用 WebRTC |
| DNS 泄露 | `dnsleaktest.com` Extended Test | 仅代理 DNS | 启用远程 DNS 解析 |
| TLS 指纹 | `openssl s_client` / JA3 工具 | 匹配 Chrome/Firefox | 使用 curl-impersonate |
| HTTP/2 帧 | `nghttp -nv` | SETTINGS 参数匹配浏览器 | 调整客户端配置 |
| 代理协议 | 检查 MTU / TCP 窗口 | 无分片异常 | 调整 MSS clamping |

四步全部通过后，Gemini 的区域校验链路应完全放行。若仍出现间歇性 403，需检查代理 IP 是否被 Google 动态标记——这种情况在共享住宅 IP 池中较为常见，需结合 [risk/scam-recovery](/risk/scam-recovery/) 中讨论的 IP 信誉监控手段持续观测。

## 双栈分流规则与代理协议选型工程实践

IPv4/IPv6 双栈环境下，分流规则的设计目标只有一个：确保发往 Google 的每一个 SYN 包都从纯净落地出口，且不因 IPv6 优先级或 DNS 解析路径产生旁路泄漏。实际操作中，大量“Gemini 无法访问”案例的根因不在于落地 IP 本身被标记，而在于客户端在双栈环境下将部分 Google 域名解析到了本地 ISP 的 IPv6 地址，绕过了代理隧道。

### 双栈泄漏的三种典型路径

**路径一：DNS 返回 AAAA 记录触发直连**。 客户端配置了 `ipv6: true` 但分流规则仅匹配 IPv4 CIDR，DNS 解析 `generativelanguage.googleapis.com` 返回 AAAA 记录后，流量按 IPv6 路由表直出。抓包表现为：代理进程无对应连接日志，但浏览器已完成 TLS 握手并收到 Google 边缘节点响应。

**路径二：Happy Eyeballs 竞速导致部分连接泄漏**。 现代浏览器和 Go runtime 默认启用 RFC 8305 Happy Eyeballs，同时发起 A 和 AAAA 查询，优先使用先返回的地址族。若 IPv6 直连 RTT 低于代理隧道 RTT，浏览器会选择直连 IPv6 路径。

**路径三：代理协议自身不支持 IPv6 出口**。 Shadowsocks 的 `outbound-bind-interface` 未绑定 IPv6 地址时，远端解析 `google.com` 得到 AAAA 记录后连接失败，回退逻辑缺失导致超时。

### Clash 分流规则配置

以下配置基于 Clash Meta 内核，核心思路是：Google 全域域名强制走代理、DNS 解析强制通过代理解析、IPv6 流量默认拒绝直连。

```yaml
dns:
  enable: true
  ipv6: true
  enhanced-mode: fake-ip
  fake-ip-range: 198.18.0.1/16
  fake-ip-filter:
    - "*.lan"
    - "*.local"
  nameserver:
    - https://1.1.1.1/dns-query
    - https://8.8.8.8/dns-query
  proxy-server-nameserver:
    - https://1.1.1.1/dns-query

proxies:
  - name: "trojan-pure"
    type: trojan
    server: your.landing.ip
    port: 443
    password: "your-password"
    sni: "www.microsoft.com"
    alpn: ["h2", "http/1.1"]
    skip-cert-verify: false
    udp: true

proxy-groups:
  - name: "Google"
    type: select
    proxies: ["trojan-pure"]

rules:
  # Google 全域强制代理，含 IPv6 字面量
  - DOMAIN-SUFFIX,google.com,Google
  - DOMAIN-SUFFIX,googleapis.com,Google
  - DOMAIN-SUFFIX,generativelanguage.googleapis.com,Google
  - DOMAIN-SUFFIX,gemini.google.com,Google
  - DOMAIN-SUFFIX,googleusercontent.com,Google
  - DOMAIN-SUFFIX,googlevideo.com,Google
  - DOMAIN-SUFFIX,gstatic.com,Google
  - IP-CIDR,142.250.0.0/15,Google,no-resolve
  - IP-CIDR6,2607:f8b0::/32,Google,no-resolve
  - IP-CIDR6,2404:6800::/32,Google,no-resolve
  # 兜底：IPv6 流量拒绝直连
  - MATCH,Google
```

关键点：`IP-CIDR6` 规则必须显式声明 Google 的 IPv6 前缀 `2607:f8b0::/32` 和 `2404:6800::/32`，并附加 `no-resolve` 避免 DNS 泄漏。`MATCH` 兜底指向代理组而非 DIRECT，防止未匹配流量走本地出口。

### Shadowsocks 与 Trojan 的抗 TLS 指纹识别对比

| 特征维度 | Shadowsocks (AEAD-2022) | Trojan |
|---------|------------------------|--------|
| 外层协议特征 | 无 TLS 握手，裸 TCP 流 | 完整 TLS 握手，与 HTTPS 不可区分 |
| 主动探测抵抗 | 2022 版引入重放保护，但无有效载荷时行为异常 | 无正确密码时回落至真实 Web 服务器 |
| TLS 指纹 | 不适用（无 TLS 层） | 依赖客户端 TLS 栈，默认 Go crypto/tls 指纹可被 JA3 识别 |
| uTLS 支持 | 不适用 | 原生支持 uTLS 指纹伪装 |
| 流量形态 | 高熵随机字节流，DF 特征明显 | 与正常 HTTPS 流量一致 |
| 抗 DPI 深度检测 | 弱，随机流易被熵检测命中 | 强，SNI 与证书链完整 |
| 适用场景 | 低审查环境、内网穿透 | 高审查环境、需 TLS 伪装的场景 |

Shadowsocks 2022 版（`2022-blake3-aes-256-gcm`）在协议层引入了会话 ID 和时间戳，解决了重放攻击问题，但其 TCP 流仍无 TLS 外层。Google 的边缘节点不直接检测代理协议，但中间 DPI 设备可识别 Shadowsocks 的流量熵特征并触发 RST。Trojan 的核心优势在于：对 Google 而言，你的流量就是一个标准的 TLS 1.3 连接，SNI 为 `www.microsoft.com`，ALPN 为 `h2`，与真实浏览器访问无异。

### TLS 指纹伪装配置

Go 标准库 `crypto/tls` 的 ClientHello 具有固定特征：扩展顺序、GREASE 值分布、椭圆曲线偏好均与 Chrome 不同。JA3 哈希可直接区分。生产环境必须启用 uTLS。

Sing-box 配置中已展示 `utls.fingerprint: "chrome"`。若使用 Xray 内核：

```json
{
  "outbounds": [
    {
      "protocol": "trojan",
      "settings": {
        "servers": [
          {
            "address": "your.landing.ip",
            "port": 443,
            "password": "your-password"
          }
        ]
      },
      "streamSettings": {
        "network": "tcp",
        "security": "tls",
        "tlsSettings": {
          "serverName": "www.microsoft.com",
          "fingerprint": "chrome",
          "alpn": ["h2", "http/1.1"],
          "allowInsecure": false
        }
      }
    }
  ]
}
```

`fingerprint: "chrome"` 使 ClientHello 的 JA3 哈希与 Chrome 126 一致。验证方法：使用 `tls.peet.ws/api/all` 检查 `ja3_hash` 是否匹配目标浏览器指纹。

### IPv6 泄漏测试方法

**方法一：浏览器端验证**。 访问 `test-ipv6.com` 或 `ipv6-test.com`，确认显示的 IPv6 地址为代理落地地址而非本地 ISP 地址。若显示本地 IPv6，说明分流规则未覆盖 AAAA 记录。

**方法二：抓包验证**。 在代理客户端所在主机执行：

```bash
tcpdump -i any -n 'ip6 and host 2607:f8b0::/32' -c 20
```

若捕获到发往 Google IPv6 前缀的包且目标 MAC 为本地网关，即为泄漏。正常情况应仅看到 TUN 接口上的封装流量。

**方法三：DNS 解析路径验证**。

```bash
dig AAAA generativelanguage.googleapis.com @127.0.0.1 -p 5353
```

若返回真实 AAAA 记录而非 fake-ip 或 NXDOMAIN，说明 DNS 查询未走代理解析。配合 `tcpdump -i any port 53` 确认是否有明文 DNS 查询发往本地 ISP 解析器。

**方法四：内核路由表检查**。 在 Linux 上执行 `ip -6 route show default`，确认默认 IPv6 路由是否指向 TUN 设备。若指向物理网卡，需通过 `ip -6 route del default dev eth0 && ip -6 route add default dev tun0` 修正，或在代理客户端启用 `strict_route`。

## 纯净落地 IP 选配与风控黑名单解除指南

落地 IP 的纯净度直接决定 Gemini 风控系统对你的信任评分。一个被 Spamhaus 收录或 IPQS 评分低于 60 的地址，即便 TLS 指纹和 WebRTC 配置完美，也会在 Google 的实时风控管道中被降权。

### IP 纯净度检测指标

评估一个 IP 是否适合作为 Gemini 落地，需要同时检查多个维度的数据。单一指标不足以做出判断，组合评分才能反映真实风险等级。

| 检测维度 | 工具/数据源 | 合格阈值 | 高风险信号 |
|---------|------------|---------|-----------|
| 欺诈评分 | IPQS (ipqualityscore.com) | ≤ 25 | > 75 |
| 代理/VPN 检测 | IPQS Proxy Detection | 未检测到 | 标记为 VPN/Proxy |
| 垃圾邮件列表 | Spamhaus ZEN (zen.spamhaus.org) | 不在列表中 | 返回 127.0.0.x |
| 滥用记录 | AbuseIPDB 置信度 | ≤ 10% | > 50% |
| ASN 类型 | IPinfo / MaxMind | ISP/Mobile | Hosting/DataCenter |
| 反向 DNS | PTR 记录 | 匹配 ISP 域名 | 无 PTR 或指向机房 |
| 黑名单收录 | DNSBL 综合查询 | 零收录 | ≥ 2 个列表收录 |
| 地理位置一致性 | IP 注册地 vs 账户区域 | 一致或邻近 | 跨洲漂移 |

IPQS 评分是最直观的单一指标。评分在 0-25 区间表示 IP 信誉良好，25-60 为灰色地带（可能被部分服务标记），60 以上基本无法通过 Google 的自动化风控。注意 IPQS 的评分存在缓存，刚更换的 IP 可能需要 24-48 小时才会刷新评分。

### 黑名单检查命令

在 Linux 环境下，可以通过 `dig` 直接查询主要 DNSBL（DNS-based Blackhole List）。以下命令批量检查一个 IP 是否被主流黑名单收录：

```bash
#!/bin/bash
IP="203.0.113.45"
REVERSED=$(echo $IP | awk -F. '{print $4"."$3"."$2"."$1}')

BLACKLISTS=(
  "zen.spamhaus.org"
  "bl.spamcop.net"
  "b.barracudacentral.org"
  "dnsbl.sorbs.net"
  "spam.dnsbl.sorbs.net"
  "cbl.abuseat.org"
  "dnsbl-1.uceprotect.net"
  "psbl.surriel.com"
)

for BL in "${BLACKLISTS[@]}"; do
  RESULT=$(dig +short ${REVERSED}.${BL} A 2>/dev/null)
  if [ -n "$RESULT" ]; then
    echo "[HIT] ${BL} -> ${RESULT}"
  else
    echo "[CLEAN] ${BL}"
  fi
done
```

Spamhaus 的返回码含义需要区分：`127.0.0.2` 表示 SBL（Spamhaus Block List），`127.0.0.3` 表示 SBL CSS，`127.0.0.4-7` 对应 XBL（Exploits Block List），`127.0.0.9` 表示 PBL（Policy Block List，动态 IP 段被收录）。PBL 收录对住宅 IP 来说较常见，但如果你的 IP 在 SBL 或 XBL 中，基本无法用于 Gemini 访问。

单次查询所有列表可以使用 `check.spamhaus.org` 的 Web 接口，但自动化场景建议直接 DNS 查询，避免 HTTP 速率限制。

### 住宅 IP 供应商对比

机房 IP（ASN 标签为 Hosting）在 Gemini 风控中几乎必然触发额外验证。住宅 IP（Residential）和移动 IP（Mobile）的 ASN 标签为 ISP，通过率显著更高。以下是主流住宅代理供应商的工程对比：

| 供应商 | IP 池规模 | 计费模式 | ASN 类型 | 支持粘性会话 | 适用场景 |
|--------|----------|---------|---------|------------|---------|
| Bright Data | 72M+ | 按流量 ($8-15/GB) | ISP + Mobile | 是（1-30min） | 高价值目标，预算充足 |
| Oxylabs | 100M+ | 按流量 ($6-12/GB) | ISP + Mobile | 是 | 大规模采集 |
| Smartproxy | 40M+ | 按流量 ($7-12/GB) | ISP 为主 | 是 | 中小规模 |
| IPRoyal | 2M+ | 按流量 ($1.75-7/GB) | ISP | 是 | 成本敏感场景 |
| 自建 4G/LTE 代理 | 取决于 SIM 卡 | 硬件+流量费 | Mobile | 固定 IP | 长期稳定使用 |

自建 4G/LTE 代理是成本最优的长期方案。一张支持公网 IP 的物联网 SIM 卡配合树莓派或 GL.iNet 路由器，可以获得运营商级 NAT 后的移动 IP。移动 IP 的 ASN 标签天然为 Mobile，Google 对其信任度高于住宅 ISP IP。缺点是 IP 可能因运营商回收而变动，需要配合 DDNS 和代理协议（参考 [protocol/trojan](/protocol/trojan/) 的配置方案）实现动态更新。

选择供应商时，务必确认其 IP 池中不包含已被 Google 标记的网段。部分低价供应商会回收被滥用的 IP，这些地址的 IPQS 评分往往已经劣化。建议在正式使用前用上述脚本对分配的 IP 做一轮黑名单扫描。

### 黑名单申诉与更换策略

IP 被列入黑名单后，有两种路径：申诉移除或直接更换。

**申诉适用场景**：IP 属于你自有的静态住宅 IP 或企业专线，被误收录。申诉前先确认收录原因——Spamhaus 的查询页面会显示收录时间和原因分类。如果是 PBL 收录（动态 IP 段），申诉通常无效，因为这是运营商网段的策略性收录，需要联系 ISP 申请静态 IP 或从 PBL 中排除。

Spamhaus 申诉模板（通过 https://www.spamhaus.org/lookup/ 提交）：

```
Subject: SBL/XBL Removal Request for 203.0.113.45

Dear Spamhaus Team,

I am the administrator of IP 203.0.113.45 (AS12345, Example ISP).
This IP has been listed in your SBL/XBL database.

We have investigated the cause and taken the following remediation steps:
1. Scanned all services on this IP for open relays and malware.
2. Updated firewall rules to block outbound SMTP on port 25.
3. Verified no compromised accounts or unauthorized access.

We kindly request removal of this IP from your blocklist.
Please let us know if additional information is required.

Best regards,
[Your Name]
[Your Organization]
```

申诉周期通常为 24-72 小时。Spamhaus 对首次申诉的处理较快，但如果是重复收录，审核会更严格。

**更换策略**：对于大多数 Gemini 访问场景，直接更换 IP 比申诉更高效。更换时遵循以下流程：

1. 从供应商处释放当前 IP，请求重新分配
2. 对新 IP 执行完整的黑名单扫描（上述脚本）
3. 检查 IPQS 评分和 ASN 类型
4. 确认 IP 的地理位置与 Google 账户区域一致
5. 在新 IP 上首次访问 Gemini 时，避免立即执行敏感操作（如修改账户设置），先进行常规搜索和问答，建立正常使用模式

如果供应商的 IP 池整体质量下降（多个 IP 均被标记），考虑切换供应商或改用自建移动代理方案。长期来看，固定一个干净的移动 IP 配合正确的 TLS 指纹配置，是维持 Gemini 稳定访问的最优解。

## Google Workspace AI 区域限制特殊考量

Workspace AI（含 Gemini for Workspace、Duet AI 遗留授权）与消费级 Gemini 在区域策略上运行于两套独立的风控管线。消费级 Gemini 以 Google Account 的注册地、支付资料和实时访问 IP 为主要判定依据；Workspace AI 则额外叠加了管理员控制台策略、企业数据区域承诺（Data Region Commitment）以及 Workspace 域级别的合规审计维度。理解这两套管线的差异，是排查企业账户 Gemini 无法访问问题的前提。

### 管理控制台中的区域与 AI 开关路径

管理员需在 Admin Console 中逐层确认以下路径的配置状态：

- **路径 A**：`admin.google.com` → 目录 → 目录设置 → 法律与合规 → 数据区域。此处决定该 Workspace 域的数据驻留区域（Data Region），可选值包括 `United States`、`Europe`、`India`、`Australia`、`Japan` 等。若域被锁定在 `Europe`，而用户实际出口 IP 落在美国，Google 后端会触发区域一致性校验失败，表现为 Gemini 侧边栏灰显或返回 `403 Forbidden`，错误码通常嵌入在 `https://workspace.google.com/ai` 的 XHR 响应体 `error.details[].reason` 字段中，值为 `DATA_REGION_MISMATCH`。
- **路径 B**：`admin.google.com` → 应用 → 附加 Google 服务 → Gemini。此处有三个独立开关：`Gemini for Workspace`（总开关）、`Allow users to access Gemini outside your domain`（跨域访问）、`Gemini data processing`（数据处理同意）。任一关闭均导致企业账户无法调用 AI 接口，且错误信息不会回显到客户端，仅在 Admin Console 的审计日志（`Reports → Audit → Gemini`）中记录 `AI_ACCESS_DENIED_BY_POLICY`。
- **路径 C**：`admin.google.com` → 账户 → 账户设置 → 辅助功能 → 服务条款。此处需确认 `Workspace AI 附加条款` 已被接受。未接受时，API 网关会在 TLS 握手后的 HTTP/2 HEADERS 帧中插入 `grpc-status: 7`（PermissionDenied），客户端表现为无限加载。

### 企业账户与个人账户风控维度对比

| 风控维度 | 消费级 Gemini | Workspace AI |
|---------|--------------|-------------|
| 区域判定依据 | 账户注册地 + 实时 IP | 数据区域承诺 + 域策略 + 实时 IP |
| IP 纯净度阈值 | 中（允许部分住宅 IP） | 高（要求企业级出口，数据中心 IP 直接拒绝） |
| ASN 白名单 | 无显式白名单 | 部分域绑定 Google Cloud Interconnect，仅允许特定 ASN |
| 支付方式 | 个人信用卡 | 企业账单账户 + 采购订单 |
| 数据驻留 | 无承诺 | 可选 US/EU/IN/AU/JP，强制校验 |
| 审计日志 | 无 | 完整 Gemini 审计日志，含请求元数据 |
| 代理容忍度 | 低 | 极低（企业出口 IP 变更需报备） |
| 错误回显 | 明确 403 或地区不可用 | 静默失败或 grpc-status 7 |

关键差异在于：消费级账户的风控是“事后拦截”，Workspace AI 是“事前策略下发”。企业域的策略配置一旦与实时网络路径冲突，Google 边缘节点会在 TCP 层直接 RST，不返回任何 HTTP 响应。此时 `curl -v https://gemini.google.com` 会显示 `Connection reset by peer`，而非 403。

### 合规数据区域列表与校验逻辑

Google 当前承诺的 Workspace AI 数据区域如下：

| 区域代码 | 地理范围 | 校验字段 |
|---------|---------|---------|
| `US` | 美国本土 | `x-goog-data-region: us` |
| `EU` | 欧盟成员国 | `x-goog-data-region: eu` |
| `IN` | 印度 | `x-goog-data-region: in` |
| `AU` | 澳大利亚 | `x-goog-data-region: au` |
| `JP` | 日本 | `x-goog-data-region: jp` |
| `CA` | 加拿大 | `x-goog-data-region: ca` |
| `GB` | 英国 | `x-goog-data-region: gb` |

校验逻辑：当用户请求到达 Google 边缘 PoP 时，边缘节点提取源 IP 的 GeoIP 数据库归属，并与 Admin Console 中设定的数据区域进行比对。若源 IP 归属区域与承诺区域不一致，边缘节点在 HTTP/2 层返回 `421 Misdirected Request`，并在 `alt-svc` 头中指示正确的区域端点。企业用户若通过代理访问，代理落地 IP 的 GeoIP 必须与数据区域承诺完全匹配。例如，域承诺 `EU`，则代理落地 IP 必须注册在欧盟成员国，且 ASN 不能是数据中心 ASN（如 AS14061、AS16509）。住宅 IP 在欧盟境内且 ASN 为 ISP 级别时，通过率显著高于机房 IP。

### 管理员排障命令

以下命令用于在管理员终端或受管设备上快速定位 Workspace AI 区域策略冲突：

```bash
# 1. 检查当前出口 IP 的 GeoIP 归属与 ASN
curl -s https://ipinfo.io/json | jq '{ip, city, region, country, org}'

# 2. 检查 Google 边缘节点返回的区域校验头
curl -sv https://gemini.google.com 2>&1 | grep -iE 'x-goog-data-region|alt-svc|grpc-status'

# 3. 检查 Workspace AI 接口的 gRPC 状态（需携带 OAuth token）
curl -sv -H "Authorization: Bearer $TOKEN" \
  https://cloudaicompanion.googleapis.com/v1/internal/health 2>&1 | grep -i grpc-status

# 4. 在受管设备上检查 Chrome 策略是否禁用了 Gemini
# Windows 注册表路径
reg query "HKLM\SOFTWARE\Policies\Google\Chrome" /v GeminiSettings

# macOS plist 路径
defaults read com.google.Chrome GeminiSettings

# 5. 检查 DNS 解析是否指向正确的区域端点
dig +short gemini.google.com
# 若返回的 IP 属于非承诺区域的 Google PoP，需调整 DNS 或代理分流规则
```

若第 2 步返回 `x-goog-data-region` 与 Admin Console 设定不符，或第 3 步返回 `grpc-status: 7`，则确认是区域策略冲突。此时需调整代理落地 IP 的 GeoIP 归属，或修改 Admin Console 的数据区域承诺。注意：数据区域承诺的修改有 30 天冷却期，频繁变更会触发 Google 的合规审计标记。

对于使用 [protocol/shadowsocks](/protocol/shadowsocks/) 或 [protocol/trojan](/protocol/trojan/) 的企业出口，需确保代理链路的每一跳均不泄露源 IP 的原始 GeoIP。WebRTC 泄露和 DNS 泄露在此场景下同样致命——即使代理落地 IP 在欧盟，若 DNS 查询走本地 ISP 且返回美国 CDN 节点，边缘节点仍会判定区域不一致。建议在企业出口部署 DNS over HTTPS 并强制走代理隧道，或在 [risk/scam-recovery](/risk/scam-recovery/) 类风控场景中预先隔离受污染 IP 段。

企业账户的额外风控维度还包括：Workspace 域的管理员账号若曾触发过 Google 的滥用检测（如批量创建用户、异常 API 调用），整个域的 AI 访问会被降级。此时 Admin Console 的 `Reports → Audit → Gemini` 中会记录 `DOMAIN_TRUST_SCORE_LOW`，需通过 Google Workspace 支持渠道提交域信任恢复申请。
